# 架构

## 一、整体链路

```
用户提问
   ↓
JWT 鉴权 + 令牌桶限流（app/guard.py）
   ↓
LangGraph 编排（app/core/graph.py）
   ├─ route        规则判意图，不调模型
   ├─ chat         闲聊
   ├─ retrieve → generate   政策问答（RAG）
   ├─ tool_order   查订单 / 查物流
   ├─ tool_refund  提交退款
   └─ handoff      转人工建工单
   ↓
SSE 流式返回（app/api/chat.py）
```

## 二、意图路由

规则判断，不调模型——省一次 LLM 往返，也让测试不依赖模型。

| 意图 | 触发条件 | 分支 |
|---|---|---|
| `handoff` | 投诉 / 人工 / 举报 / 差评 | 建工单 |
| `refund` | 退款退货类词 + 动作词（我要/帮我/申请） | 提交退款 |
| `order` | 强查件词，或弱领域词 + 动作词，或有订单号 | 查订单或物流 |
| `chat` | 你好 / 在吗 / 谢谢 | 闲聊 |
| `rag` | 其余全部 | 检索 + 生成 |

### 强弱词分级

「物流」既是领域词也是意图词——「物流三天没更新怎么办」问的是政策，「我的快递到哪了」问的是查件。所以拆成两级：

```python
_ORDER_STRONG = ("到哪", "查件", "物流信息", "快递单号", "物流单号")   # 出现就是查件
_ORDER_WEAK   = ("物流", "快递", "签收", "配送", "发货", "订单")       # 必须配动作词
```

判定顺序：

```python
if 投诉词: return "handoff"
if 退款词 and 动作词: return "refund"     # 退款优先于订单
if 强查件词: return "order"
if 有订单号: return "order"
if 弱领域词 and 动作词: return "order"
if 闲聊词: return "chat"
return "rag"
```

### 为什么不用模型兜底

试过「规则判不出来时调微调模型分类」，回归集从 16/20 掉到 **11/20**。

原因：cs-lora 被 SFT 成客服助手后，看到「退货」「假货」就倾向判成办事分支——

| 查询 | 期望 | 模型判成 |
|---|---|---|
| 退货要几天到账 | rag | refund |
| 刚买就降价能退差价吗 | rag | refund |
| 买到假货怎么赔 | rag | handoff |
| 帐篷漏水怎么办 | rag | handoff |

**微调模型的先验被改变了，做分类反而不如规则。** 已回滚。

### 另外两个关键设计

1. **退款优先于订单**：「我要退款，订单 O10001」走退款，不被订单号抢走
2. **政策问答和办事分开**：「退货要几天到账」无动作词 → 走检索；「我要退货」有动作词 → 走工具

## 三、检索链路（三路召回 + RRF + 精排）

```
query
 ├─ ① FAQ 精确匹配    权重 1.2  归一化后查哈希表
 ├─ ② 稠密向量        权重 1.0  bge-m3 1024 维，Milvus COSINE
 └─ ③ 稀疏向量        权重 0.8  bge-m3 lexical_weights，Milvus IP
        ↓
   加权 RRF 融合（k=60）
        ↓
   bge-reranker-v2-m3 精排
        ↓
   top-k 送生成
```

**为什么第一路是 FAQ 精确匹配**：客服场景里大量问题是 FAQ 原句或近似原句，直接命中标准答案比向量检索更准，还能压住长尾误召回。这一路不需要模型，本地就能测。

**为什么用 RRF 不用分数加权**：余弦相似度和稀疏内积量纲不同，直接加权没有物理意义。RRF 只看名次，规避这个问题。

## 五、数据权限

JWT 只解决「你是谁」，真正的价值是 **user_id 由服务端签发、用户改不了**，可以放心当数据过滤条件。

```python
# app/core/tools.py
if not order or order.user_id != user_id:
    return None      # 越权一律当「订单不存在」
```

不区分「没这个单」和「不是你的单」——否则能通过报错差异探测别人的订单号。

## 六、限流：Redis 令牌桶

只对 `/api/chat` 限流——LLM 调用贵（每次约 2 秒），查订单走 MySQL 几十毫秒不需要保护。

```lua
-- 令牌桶：容量 5，按 20/分钟补充，Lua 保证原子性
local data = redis.call('HMGET', key, 'tokens', 'ts')
...
redis.call('EXPIRE', key, 120)
```

| 参数 | 值 |
|---|---|
| 用户级速率 | 20 次/分钟 |
| 突发容量 | 5 |
| 存储 | `rl:user:{user_id}` 哈希 |

**降级策略**：Redis 挂了直接放行（`except: return True`）。限流是保护措施，不能因为它挂了把业务打挂。

实测：连续 7 次 chat → `200 200 200 200 200 429 429`。

## 七、为什么用纯 ASGI 中间件

```python
class RequestContext:
    async def __call__(self, scope, receive, send):
        ...
        await self.app(scope, receive, send_wrapper)
```

不用 `BaseHTTPMiddleware`：它会额外套一层 task，导致 SSE 里 `request.is_disconnected()` 失效。纯 ASGI 只包装 `send`，流式不受影响。
