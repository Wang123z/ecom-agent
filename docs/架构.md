# 架构

## 一、整体链路

```
用户提问
   ↓
JWT 鉴权 + 令牌桶限流（app/guard.py）
   ↓
LangGraph 编排（app/core/graph.py）
   ├─ route        规则判意图，不调模型
   ├─ chat         闲聊
   ├─ retrieve → generate   政策问答（RAG）
   ├─ tool_order   查订单 / 查物流
   ├─ tool_refund  提交退款
   └─ handoff      转人工建工单
   ↓
SSE 流式返回（app/api/chat.py）
```

## 二、意图路由

规则优先，不调模型——省一次 LLM 往返，也让测试不依赖模型。

| 意图 | 触发条件 | 分支 |
|---|---|---|
| `handoff` | 投诉 / 人工 / 举报 / 差评 | 建工单 |
| `refund` | 退款退货类词 + 动作词（我要/帮我/申请） | 提交退款 |
| `order` | 物流 / 快递 / 到哪 / 订单 | 查订单或物流 |
| `chat` | 你好 / 在吗 / 谢谢 | 闲聊 |
| `rag` | 其余全部 | 检索 + 生成 |

**两个关键设计：**

1. **退款优先于订单**：「我要退款，订单 O10001」走退款，不被「订单」抢走
2. **政策问答和办事分开**：「退货要几天到账」无动作词 → 走检索；「我要退货」有动作词 → 走工具

## 三、检索链路（三路召回 + RRF + 精排）

```
query
 ├─ ① FAQ 精确匹配    权重 1.2  归一化后查哈希表
 ├─ ② 稠密向量        权重 1.0  bge-m3 1024 维，Milvus COSINE
 └─ ③ 稀疏向量        权重 0.8  bge-m3 lexical_weights，Milvus IP
        ↓
   加权 RRF 融合（k=60）
        ↓
   bge-reranker-v2-m3 精排
        ↓
   top-k 送生成
```

**为什么第一路是 FAQ 精确匹配**：客服场景里大量问题是 FAQ 原句或近似原句，直接命中标准答案比向量检索更准，还能压住长尾误召回。这一路不需要模型，本地就能测。

**为什么用 RRF 不用分数加权**：余弦相似度和稀疏内积量纲不同，直接加权没有物理意义。RRF 只看名次，规避这个问题。

## 五、数据权限

JWT 只解决「你是谁」，真正的价值是 **user_id 由服务端签发、用户改不了**，可以放心当数据过滤条件。

```python
# app/core/tools.py
if not order or order.user_id != user_id:
    return None      # 越权一律当「订单不存在」
```

不区分「没这个单」和「不是你的单」——否则能通过报错差异探测别人的订单号。

## 六、为什么用纯 ASGI 中间件

```python
class RequestContext:
    async def __call__(self, scope, receive, send):
        ...
        await self.app(scope, receive, send_wrapper)
```

不用 `BaseHTTPMiddleware`：它会额外套一层 task，导致 SSE 里 `request.is_disconnected()` 失效。纯 ASGI 只包装 `send`，流式不受影响。

## 七、目录职责

| 目录 | 职责 | 依赖 |
|---|---|---|
| `app/config.py` | 配置集中，无硬编码路径 | — |
| `app/guard.py` | JWT + 令牌桶 | Redis（可降级） |
| `app/api/` | 路由层，只做参数校验与响应 | — |
| `app/core/` | 编排、工具、状态 | 业务库、检索 |
| `app/core/rag/` | 三路召回 + 融合 | Milvus、bge |
| `app/infra/` | 外部依赖封装 | Milvus / MySQL / LLM |
| `train/` | 数据流水线与训练 | torch |
| `eval/` | 指标、裁判、一键评测 | — |
| `deploy/` | compose、vLLM 启动、压测 | Docker |
