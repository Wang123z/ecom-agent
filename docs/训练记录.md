# 训练记录

四轮 SFT 迭代的完整数据。硬件：RTX 4090 24G，Qwen3-8B，LoRA。

## 一、总览

| 轮次 | 数据量 | 知识点 | rank | trainable% | 最优 eval_loss | 峰值显存 | 耗时 |
|---|---|---|---|---|---|---|---|
| 1 | 400 | 400 | 16 | 0.84% | 0.741（epoch 2） | 4.3 GB（0.6B） | 2 分钟 |
| 2 | 1200 | 400 | 16 | 0.53% | 0.405（epoch 2） | 16.4 GB | 7.5 分钟 |
| 3 | 1600 | 533 | 16 | 0.53% | 0.418（epoch 2） | 16.4 GB | 23 分钟 |
| 4 | 1640 + 40 对冲 | 533 | **32** | 1.05% | 0.424（epoch 2） | 17.2 GB | 26 分钟 |

> 第 3、4 轮的 eval_loss 不能和第 2 轮直接比——val 集随数据扩充而变化，样本难度不同。

## 二、每轮的问题与解法

### 第 1 轮：400 条，数据太少

**现象**：`吊牌剪了能退吗` 答「可以，但可能影响售后」——与政策相反。

**诊断**：每个知识点只出现 1 次，模型只学到高频模式（如「1-3 个工作日」在多条样本里重复出现，被记住），长尾知识全丢。

**解法**：扩到 1200 条，每个知识点 3 种问法。

### 第 2 轮：1200 条，密度假设成立

**现象**：吊牌答对了，且能自己组织语言（「不受吊牌影响」不在训练数据里）。但 `物流三天没更新` 和 `物流停了一周` 串台，答成了同一件事。

**诊断**：密度翻 3 倍有效；但相似知识点区分不足。

**解法**：加边界知识点 + 6 个新品类。

### 第 3 轮：1600 条，效果反而退化

**现象**：吊牌又答错（「可以，不影响退换」），奶粉答成「未开封可 7 天无理由」——都是基座模型的通用常识，不是我们数据里的政策。

**诊断**：

1. 「吊牌」在数据里出现 22 次，其中 19 次是「吊牌完好可退」，只有 3 次是「剪了不能退」——**信号被稀释**
2. rank 16 的容量撑不住 1600 条 × 27 类知识，模型退化成给「平均答案」

**解法**：rank 16 → 32，同时补对冲数据。

### 第 4 轮：1640 条 + 对冲 + rank 32

**对冲数据的设计**：同一商品不同状态，答案相反，成对出现。

```
吊牌完好的衣服能退吗  → 可以
吊牌剪了的衣服能退吗  → 不支持

没拆封的奶粉能退吗    → 不支持（食品类一律不退）
拆封的奶粉能退吗      → 更不支持

物流48小时内没更新    → 正常
物流超过48小时没更新  → 异常，点催发货
物流一周没动          → 严重异常，查件退款
```

20 组对子，逼模型学「看状态判断」而不是「吊牌 → 能退」。

**结果**：6 条测试 5 对 1 偏。

## 三、第 4 轮测试明细

| 问题 | 模型回答 | 判断 |
|---|---|---|
| 吊牌剪了能退吗 | 吊牌剪掉后一般不支持无理由退货…但质量问题不影响售后 | ✓ |
| 吊牌完好的能退吗 | 吊牌完好的可以退 | ✓ |
| 奶粉能退吗 | 奶粉属食品类，签收后不支持7天无理由退货 | ✓ |
| 物流三天没更新怎么办 | 超过48小时无更新可联系客服核实 | ✓ |
| 物流停了一周怎么办 | 属于严重异常，联系客服核实单号状态 | ✓ |
| 帐篷漏水怎么办 | 讲怎么补，建议联系厂家售后 | △ 方向偏但合理 |

**最关键的一条**：同一个词「吊牌」，模型给出了相反答案。说明学到的是状态判断，不是关键词记忆。

## 四、踩过的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| Qwen3 模板无条件插 `<think>` | 训练数据里每条 assistant 前都有空思考块 | 渲染后正则剥离，训练用 text 字段而非 messages |
| `apply_chat_template(tokenize=True)` 返回 dict | `len()` 得到 2 而不是 token 数 | 先渲染成文本再分词 |
| epoch 3 过拟合 | eval_loss 在 epoch 2 触底后回升 | 取 epoch 2 的 checkpoint；rank 32 时回升更明显（+0.027），说明该用 2 epoch |
| vLLM `max_lora_rank` 默认 16 | rank 32 的 adapter 加载失败 | `--max-lora-rank 32` |
| 两份 cuDNN 冲突 | `Found 2 libcudnn.so.x` | 卸掉不匹配的 `nvidia-cudnn-cu12`（torch 是 cu130） |
| flashinfer JIT 编译失败 | `nvcc fatal: Unknown option '--compress-mode'` | 系统 nvcc 12.1 太老，用 `VLLM_USE_FLASHINFER_SAMPLER=0` 绕开 |
| 无卡模式内存只有 2 GB | 加载 tokenizer 就被 OOM 杀掉 | 模型相关操作必须开卡 |
| val 与 train 同文件 | DPO 等于在训练集上评估 | build_dpo 切 10% 到 `preference_val.jsonl` |

## 五、参数选择的依据

| 参数 | 取值 | 依据 |
|---|---|---|
| LoRA rank | 32 | 16 撑不住 1600 条 × 27 类；32 后 params 从 4364 万涨到 8729 万 |
| alpha | 64 | 保持 alpha/rank = 2 的常规比例 |
| target_modules | 全部线性层 | q/k/v/o + gate/up/down，覆盖注意力与 FFN |
| lr | 2e-4 | LoRA 常用区间，配合 cosine + 0.1 warmup |
| epochs | 3 → 应改 2 | eval_loss 在 epoch 2 触底，epoch 3 回升 |
| max_length | 2048（SFT）/ 1024（DPO） | token p50 约 72，2048 足够；DPO 双 adapter 显存紧，降到 1024 |
| batch × grad_accum | 1 × 8 | 有效 batch 8，24G 显存下 bs=1 最稳 |

## 六、结论

1. **数据密度比数据总量重要**：400 → 1200 条（每知识点 1 → 3 问法）带来的提升，远大于单纯增加新知识点。
2. **少数派知识需要显式对冲**：只写「吊牌剪了不能退」不够，必须同时写「吊牌完好可以退」，模型才能学到边界。
3. **LoRA 容量是硬约束**：rank 16 在 1600 条时出现容量瓶颈，表现为「给平均答案」。
4. **eval_loss 低 ≠ 答得对**：第 3 轮 eval_loss 0.418 看起来不差，但实际答错关键问题。必须做点对点测试。
5. **跨 val 集的 eval_loss 不可比**：数据一变，val 集就变，指标失去可比性。要比较必须固定评测集。
